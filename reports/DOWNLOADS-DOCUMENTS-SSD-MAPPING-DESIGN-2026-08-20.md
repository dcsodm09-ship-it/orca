## 执行摘要

`~/Downloads` 当前是一个指向已丢失的 `dh-work.sparseimage` 镜像的悬空符号链接（自 2026-07-18 起断裂，其中可能存在的历史下载文件在本机层面已事实性不可寻回，且这是先于本次任务已经存在的既成事故，不是本次迁移会造成的新损失）；`~/Documents` 是内置盘上一个真实的 196MB/12 项目录，其中包含合同、密钥文件等不可再生的个人数据。本设计的目标是把这两个位置的真实内容迁移到已加密、已挂载的 Extreme SSD 上，原路径改为指向 SSD 的符号链接，沿用仓库中 `.claude`/`.codex` 等 19 个现存符号链接、以及 Android 重数据迁移脚本已验证过的"两阶段、fail-closed、可回滚"纪律：Phase A 无损复制到 SSD staging → 人工审阅逐项哈希校验结果 → Phase B 原子替换（改名保留，绝不删除）。

**本文档是一份设计（DESIGN）文档。** 撰写与调研过程中只执行了只读检查（`ls`/`stat`/`diskutil`/`defaults`/`mount`/`tmutil`/`launchctl` 等），没有对 `~/Downloads`、`~/Documents`、`dh-work` 或 Extreme SSD 上的任何内容做过写入、改名、复制或删除；本机现状与调研开始前完全一致。本设计**不构成执行授权**——第 5 节列出了 7 个必须由用户逐一显式批准的人工确认检查点（授权点 0 至 6），在对应检查点被批准之前，配套脚本只允许运行只读预检模式，不带 `--execute` 不产生任何实际变更；任何实际的复制、改名、建符号链接命令都必须在拿到对应授权后才能运行。

相较于最初的草案，本版本额外补齐了四处曾被独立对抗性复核指出的缺口，并已直接落进正文（而非作为附加的注意事项列表）：(1) 明确记录并设计应对"改名与建链接之间遭遇 kill -9/断电"这一无法被进程内异常处理捕获的崩溃窗口，新增 `heal` 子命令弥补自动回滚在该窗口内的失效；(2) 把只读哨兵脚本的检测逻辑从"路径能否解析"升级为"路径是否仍是指向预期 SSD 目标的符号链接"，使其真正能捕捉 iCloud Drive 静默重建 Documents 符号链接（而非仅仅"SSD 拔出"）这一风险；(3) 把 Downloads 现有断链符号链接的处置正式纳入编号的 Phase A0 步骤，使用与全流程一致的 fsync/日志化改名，而不是留作脚本纪律之外的散文承诺；(4) 修正了对 Finder 在符号链接目标缺失时具体表现的过度自信描述，改为如实反映终端层面已验证的行为，并明确 GUI 层面尚未实测。

## 1. 现状与目标精确定位

### 1.1 Downloads 的真实状态——一个已经断裂的既有迁移，而非全新任务

`~/Downloads` **当前已经是**一个符号链接：

```
/Users/www1adwawd/Downloads -> /Volumes/dh-work/_mac_migrated/Users/www1adwawd/Downloads
```

创建于 2026-07-18 16:51:44。它指向的 `dh-work` 不是一块物理外置盘，而是原本应该由 LaunchAgent (`com.user.dh-work.mount`) 在每次登录时通过

```
hdiutil attach -nobrowse -mountpoint /Volumes/dh-work /Volumes/Extreme SSD/dh-work.sparseimage
```

挂载起来的**磁盘映像文件**。该 LaunchAgent 目前处于已加载但未运行状态（PID 为空）。这个映像文件本该存放在当前正健康挂载着的 Extreme SSD 上——但它现在**不在那里**，且经过：

- `diskutil` / `mount` / Spotlight (`mdfind`) 全盘搜索
- 7 天统一日志回溯
- `/Volumes/Extreme SSD/.Trashes/501` 检查

均未在这台机器任何可达位置找到该文件的踪迹。这不是"外置盘没插好"，而是**镜像文件本体缺失**，且无法从本机确定它是被删除、改名，还是从未完整迁移到 SSD 上。

**这意味着什么**：`dh-work` 卷里可能存在的历史下载文件（自 7 月 18 日符号链接建立以来所有原本会落在 `~/Downloads` 的文件），在本机层面**目前处于事实上不可寻回的状态**。这不是本次迁移会造成的新损失，而是**已经发生、且早于本次任务存在**的既成风险——必须先向用户挑明，而不能被新的迁移设计"顺手带过"。

**我的建议与理由**：**不要**把"先找回 dh-work 内容"设为本次迁移的前置阻断步骤去主动执行恢复动作（例如尝试 `hdiutil` 各种探测式挂载、扫描裸设备找残留 sparseimage 结构等）——这类操作本身有进一步破坏可能残留证据的风险，且成功率未知，应作为一个完全独立的"数据取证/恢复任务"，而不是揉进"把 Downloads 挂到 SSD 上"这个结构性迁移任务里。本设计对 Downloads 的处理方式是：**将当前这个已经指向不可达目标的符号链接视为"待处置的旧记录"，用与全流程完全同等纪律的方式原样保留/改名备份（不删除，见第 3.0.5 节 Phase A0），再另起一个全新的、指向 SSD 真实目录的 Downloads**。是否要另外单独立项尝试恢复 dh-work.sparseimage，是一个必须由用户拍板的独立决定（见第 5 节授权点 0），本设计不擅自决定放弃或坚持恢复。

**在授权点 0 的决定做出之前，不得对 `~/Downloads`（包括当前那个坏符号链接本身）做任何改动**——包括看起来"无害"的手动 `rm` 或改名；具体的、被纳入审计流水线的处置动作见第 3.0.5 节。

### 1.2 Documents 的真实状态

`~/Documents` 是一个**真实的本地目录**（非符号链接），位于内置系统盘的 Data 卷，**196MB，12 个平铺条目（11 个真实文件 + `.DS_Store`）**，内容包括合同文档（.docx）、招聘/产品 PDF、一个 20MB 的 Excel、一个 137MB 的 dmg 安装包、一个 1.4MB 的 zip，以及**两个文件名疑似 GCP service-account 密钥的 JSON 文件**（未被本次调研打开或读取内容，仅按命名模式识别，作为附带安全提示写入第 6 节风险清单，不属于本次迁移要处理的问题）。

关于 iCloud"桌面与文稿"同步：调研通过 `defaults read com.apple.finder` 确认 `FXICloudDriveDesktop=0`、`FXICloudDriveDocuments=0`（同步功能本身是关的），并直接核对了 `~/Library/Mobile Documents/com~apple~CloudDocs/` 下确实**没有** `Desktop`/`Documents` 子目录（这是该功能开启时 macOS 会自动创建的位置）。但同时，`FXICloudDriveEnabled=1`——即 **iCloud Drive 总开关是开着的**，而调研引用的社区证据显示：**仅仅打开 iCloud Drive 总开关（不需要额外打开"桌面与文稿"同步）就可能导致 macOS 在下次登录/重启时清理掉 `~/Documents` 位置上的符号链接**，这条结论没有被本机的 `defaults read` 检查覆盖到，也没有被 100% 证实或证伪。

**因此，本设计明确要求：迁移 Documents 之前，必须由人工执行以下确认动作，本设计不代替用户做这个假设**：

1. 打开 系统设置 → Apple 账户 → iCloud → iCloud Drive → 选项，用**肉眼**确认"桌面与文稿资料夹"复选框处于未勾选状态（不仅仅信任 `defaults read` 的结果，因为 GUI 状态是最终权威，`defaults` 只是同一份状态的一个读出口，历史上出现过两者不同步的案例报告）。
2. 明确知晓并接受"即使这个复选框是关的，iCloud Drive 总开关本身开着，仍有真实（虽未 100% 权威文档化）的风险会导致系统在某次登录时重建 `~/Documents`"这条结论后，再决定是否继续（见第 5 节授权点 1）。
3. Documents 迁移执行后，**必须**做一次真实的 logout/login 与一次 reboot 存活测试（见第 4 节 c 与第 6 节 R4），并且从 Phase B 完成的那一刻起持续受第 4 节 e 所述的、经过升级的只读哨兵保护（不能"符号链接建好当场能用就算完成"）。

### 1.3 目标的精确定义

把 `~/Downloads` 和 `~/Documents` 两个目录的**真实内容**迁移到 Extreme SSD 上，原路径改为指向 SSD 的符号链接——与 `.claude`、`.codex` 等 19 个现存条目完全同构的模式，目的是缓解内置系统盘 91% 满（18GiB 可用）的压力，同时不丢失任何一个字节的现有数据，且迁移动作本身可完全回滚。

**不属于本次目标**：恢复 dh-work.sparseimage 中的历史文件（见 1.1，需单独立项）；解决 Safari/沙盒 App 对符号链接的兼容性问题（见第 4 节，属 Apple 自身实现限制，本设计只做"验证 + 告知残余成本"，不做底层修复）；建立 Time Machine/独立备份覆盖 SSD 内容（见第 4 节 c，作为明确标注的后续独立任务）。

## 2. 是否会撞上 §3 "SSD 原生存储与 PTY 沙箱" 的 BLOCKED_APPLE_ENTITLEMENT

**结论：不会，这是两类性质完全不同的问题。**

backlog 第 3 节被 `BLOCKED_APPLE_ENTITLEMENT` 卡住的三个候选（`ssd-native-storage-closure`、`ssd-pty-lifetime-closure`、`ssd-runtime-closure`）解决的是**Orca 自身内部引擎**的问题：Orca 在自己创建/克隆 git worktree、或自己 spawn PTY 子进程时，要用 EndpointSecurity system extension + 签名代码要求（`xpc_connection_set_peer_code_signing_requirement`）在**内核层**强制这些内部写操作只能落在 SSD 边界内，防止 TOCTOU/符号链接替换攻击。这需要一个经苹果签名、公证、拥有 EndpointSecurity/system-extension entitlement 的打包 App 才能做到——这正是它被卡住的原因。

而"把 `~/Downloads`/`~/Documents` 符号链接到 SSD"是**普通用户态文件系统操作**：`os.rename` + `chmod` + `os.symlink`，不涉及 XPC、不涉及 system extension、不需要 EndpointSecurity 授权。更重要的是，这个模式**已经在生产环境里跑着**——`.claude`、`.codex`、`.agents` 等 19 个现存符号链接就是用这套普通用户态操作实现的，没有用到任何 EndpointSecurity 机制，且长期稳定运行。

所以：**§3 的阻断项与本次任务无关，不应被误判为"这个也走不了"**。本次任务应参考 `migrate_android_heavy_data_to_ssd.py` + `switch_android_heavy_data_to_ssd.py` 这一对已验证的两阶段脚本所建立的纪律（第 3 节展开），不需要等待、也不受 Apple entitlement 阻断项解除与否的影响。**但需要注意**：本设计不是对这两个脚本的逐字复用——第 3.2 节会指出这两个脚本在"改名与建链接之间遭遇进程被杀/断电"这一具体窗口上存在一个未被自动回滚覆盖的缺口，本设计为新脚本（`migrate_user_home_folder_to_ssd.py` / `switch_user_home_folder_to_ssd.py`）额外要求补上这一点，而不是原样照搬。

## 3. 具体迁移步骤

参考仓库里 Android 重数据迁移那对脚本已经验证过的"两阶段、fail-closed、可回滚"纪律：**Phase A0（仅 Downloads：先把现有断链原样退休进审计流水线）** → **Phase A（无损复制到 SSD staging，完全不碰原目录）** → 人工审阅校验结果 → **Phase B（原子替换：原目录改名保留 + 建符号链接）**。以下按同样的结构展开，并把用户全局规则要求的"加密/解锁/卷标识匹配/所有权"四项检查逐一落到具体命令。

### 3.0 目标路径设计

建议目标路径为：

```
/Volumes/Extreme SSD/UserHome/Downloads
/Volumes/Extreme SSD/UserHome/Documents
```

**不要**把这两个目录塞进 `/Volumes/Extreme SSD/Orca/local-homes/` 里。理由：`local-homes` 现有的 21 个条目语义上都是"Orca/Claude/Codex 等工具的运行时状态"——理论上可以被工具自己重建或至少是工具管理的配置/缓存数据；而用户的 Downloads/Documents 是**不可再生的真实个人数据**（合同、密钥文件、产品资料），两者的生命周期语义、未来的清理策略、备份优先级都不同，混在一起会给将来"清理 local-homes 下过期内容"这类操作带来误删真实数据的风险。单独开一个 `UserHome` 根目录，把这个边界从物理路径上就划清楚。

### 3.0.5 Phase A0（仅 Downloads）——现有断链的正式退休

`~/Downloads` 当前是一个指向不可达目标的符号链接，而下面 3.1 节描述的"源目录真实性检查"（沿用 Android 脚本模式）要求源在 Phase A 开始时必须是一个普通目录，遇到符号链接会直接判定为异常并中止。如果把"先处置这个旧符号链接"仅仅留在 1.1 节的说明文字里，而不纳入带编号、带日志的正式步骤，就会出现"实际操作时随手一个 `rm ~/Downloads` 就把它删了"的风险——这不仅违反"不删除、只改名保留"的总原则，更严重的是会摧毁 `/Volumes/dh-work/_mac_migrated/Users/www1adwawd/Downloads` 这最后一条磁盘上的线索，而这条线索正是授权点 0(b) 选择"另立专项尝试恢复 dh-work"时唯一可能用得上的取证起点。

因此，本设计把这一步骤正式纳入编号流程，作为 Phase A 之前必须先完成、且同样受第 5 节授权点约束的独立步骤：

1. **前置条件**：仅在用户已就授权点 0 做出决定（无论是 (a)/(b)/(c) 哪一种）之后才能执行本步骤；三种决定下 Phase A0 的动作完全相同（都是"改名保留，不删除"），差别只在于是否会有后续独立的 dh-work 取证任务读取这条 retained 记录。
2. **只读预检**：`os.path.islink(~/Downloads)` 必须为真；`os.readlink(~/Downloads)` 读出的目标字符串必须与 1.1 节记录的 `/Volumes/dh-work/_mac_migrated/Users/www1adwawd/Downloads` 完全一致（防止在两次调研之间该符号链接已被别的进程改写，出现不是预期中的"已知断链"）。
3. **日志先行**：在改名前，把当前 `readlink` 结果、符号链接的 `lstat` 元数据（含创建时间、属主）写入 `0600` 权限、fsync 落盘的 `PHASE_A0.json`，路径与 3.2 节的事务日志同一约定目录下。
4. **原子改名**：`os.rename(~/Downloads, ~/Downloads.orca-dh-work-broken-retained-<ts>-<nonce>)`，`fsync` 父目录。这一步只是把断链移到新名字下，**不 unlink、不删除**，退休后的断链本体连同它记录的"曾经指向哪里"这条元数据被完整保留。
5. **新建空目录**：`os.mkdir(~/Downloads)` 建一个全新的空目录，作为 3.1 节 Phase A 意义上的"源目录"（内容为空，这是预期的——Downloads 里当前活跃可用的内容本来就是零，因为符号链接本已断裂多时）。
6. **完成标记**：写 `0600` 的 `PHASE_A0_DONE.json`，记录 retained 路径、原符号链接目标字符串、时间戳，供后续 Phase A/B 及任何独立 dh-work 取证任务引用。
7. **失败处理**：第 2 步预检失败（发现不是预期断链）直接中止，不做任何改动，升级为需要人工重新调研当前 `~/Downloads` 究竟是什么状态；第 4/5 步之间若中断，恢复动作是显式的、有编号的——检测到"`~/Downloads` 不存在，但存在一个 `.orca-dh-work-broken-retained-*` 目录且没有对应 `PHASE_A0_DONE.json`"这一特征组合时，重跑本步骤的第 5 步（重建空目录）即可继续，不需要回滚已经完成的改名。

完成 Phase A0 后，`~/Downloads` 就是一个全新的、空的、真正的普通目录，满足 3.1 节"源目录真实性检查"的前提，Downloads 和 Documents 从这一步开始才在 Phase A/B 流水线里被完全同等对待。

### 3.1 Phase A ——预检 + 无损复制（脚本骨架：`migrate_user_home_folder_to_ssd.py`）

**四项全局规则检查**（用户全局规则："迁移或清理前必须验证目标卷已加密、已解锁、卷标识匹配、所有权启用，并保留可恢复副本"），逐项落地为脚本执行前的硬性前置条件，任一失败 = 整个脚本立即中止、不做任何写入：

| 检查项 | 具体命令 | 通过标准 | 失败行为 |
|---|---|---|---|
| **已加密** | `diskutil apfs list` 定位 Extreme SSD 所在 APFS 容器，查看 `FileVault` 字段；辅以 `diskutil info "/Volumes/Extreme SSD" \| grep -i "FileVault\|Encrypt"` | 显示已启用 FileVault/加密 | 中止，报告"SSD 未加密，需先在磁盘工具中启用 FileVault 后才能迁移含合同/密钥文件的 Documents"（本项必须作为脚本运行时的实时读取项，不能假设当前状态永远不变） |
| **已解锁** | `diskutil apfs list` 中该卷的 `Locked` 字段，或 `diskutil info` 中 `FileVault: Yes (Unlocked)` | 显示 Unlocked | 中止，要求用户先在 Finder/磁盘工具手动解锁，脚本绝不内置密码做程序化解锁 |
| **卷标识匹配** | 在**设计/授权阶段**先记录一次 `diskutil info "/Volumes/Extreme SSD/" \| grep "Volume UUID"`，把该 UUID 硬编码为脚本里的期望常量；每次运行时重新读取当前挂载的 UUID 并做字符串精确比对 | 完全一致 | 中止，防止"同名但不同一块盘"被误当成目标（例如 SSD 被重新格式化，或另一块同名盘被误插） |
| **所有权已启用** | `diskutil info "/Volumes/Extreme SSD/" \| grep "Owners Enabled"` | 显示 `Yes` | 中止；因为若所有权未启用，后续对 retained 备份目录做的 `chmod` 只读保护、以及复制后文件的属主/权限位都不可靠地被系统忽略，符号链接迁移的"只读退休备份"这个安全屏障会失效 |
| **保留可恢复副本** | 不是一次性检查，而是贯穿整个设计的强制约束：Phase A 只做纯新增（原目录完全不动，SSD 上新增一份），Phase B 用"改名保留"代替"删除"（见 3.2） | 全程原目录/备份目录任一时刻都存在且完整 | 见 3.2 的自动回滚与 `heal` 子命令 |

其余预检（参考 Android 脚本已验证的模式）：

- **空间余量**：目标盘可用空间 ≥ 2×源目录当前大小 + 10% + 1GiB 缓冲（`du -sh` 已知 Documents 196MB；Downloads 在完成 3.0.5 的 Phase A0 后是全新空目录，无历史数据需要合并）。
- **停止写入闸门（idle gate）**：
  - `lsof +D ~/Documents`、`lsof +D ~/Downloads` 必须返回空，确认没有进程正打开其中文件。
  - 针对 Downloads 额外扫描是否存在 `*.download` / `*.crdownload` / `*.part` 等浏览器"下载中"占位文件，存在则视为"仍在写入"，中止。
  - 进程清单检查：确认没有 Finder 正在对该目录做批量操作（可选，best-effort）。
- **源目录真实性检查**：确认源当前确实是普通目录而非符号链接（Documents 天然满足；Downloads 在完成 3.0.5 后同样满足）。
- **脚本自身完整性**：记录脚本自身 sha256，写入完成/失败标记，便于事后审计跑的是哪个版本。

**复制**：使用 `ditto --rsrc --extattr --acl` 完整复制到 SSD 上一个全新的、迁移前不存在的 staging 目录（若目标已存在则拒绝执行，避免覆盖已有内容）。选用 `ditto` 而非 `cp -a` 是因为研究明确指出它对 APFS 元数据/扩展属性/ACL 的保留更完整，其中包括对 Downloads 里未来新下载文件的 `com.apple.quarantine` 隔离标记——**这个标记必须保留**，否则迁移后 Gatekeeper 可能对这些文件的"已检查"状态产生误判。

**校验（不能只比文件数量）**：分别在复制**前**和复制**后**对源目录建一份完整清单（每个文件的 sha256、大小、mtime、扩展属性列表），断言复制前后源目录清单完全一致（证明复制过程中源没有被并发写入）；再对 SSD 上的 staging 目录建同样清单，与源目录清单逐项比对，要求除**明确声明的容差字段**外完全一致：
- 容差字段：`allocated_bytes`（APFS 克隆写时复制导致的分配字节数天然不同）、`com.apple.provenance`（系统在复制时会重写该属性值本身合法）。
- **非容差字段**：`com.apple.quarantine`（下载来源标记）、所有 ACL、内容 sha256、mtime——这些必须逐项精确相等，任何不相等都判定 Phase A 失败。

**原子发布**：`os.rename(staging_dir, final_dir)`（同一 SSD 文件系统内的原子改名），随后 `fsync` 父目录，写入 `0600` 权限的 `COMPLETED.json`，记录脚本 sha256、清单哈希、容差声明、SSD UUID。

**失败处理**：任何异常都写 `0600` 的 `FAILED.json` 并原样抛出；不留半发布状态；原目录在整个 Phase A 期间自始至终未被触碰。

### 3.2 Phase B ——原子替换（脚本骨架：`switch_user_home_folder_to_ssd.py`）

1. **预检**：重新完整跑一遍 3.1 的四项全局规则检查（不复用 Phase A 缓存结果——两个阶段可能相隔数天，SSD 状态可能已变化）；重新跑 idle gate；重新校验 Phase A 留下的 `COMPLETED.json` 标记（UUID、路径、脚本哈希是否吻合当前实际状态）；对当前源目录、SSD 上的 staging/final 目录重新建清单并与 `COMPLETED.json` 记录的清单比对，若有任何漂移（例如 Phase A 之后用户又往 Documents 里存了新文件）则中止，要求重跑 Phase A。
2. **事务日志**：在任何写入动作之前，把改名目标路径、四项预检的完整证据写入 `0600` 权限的 `PREIMAGE.json`，路径固定为 `/Volumes/Extreme SSD/Orca/recovery/user-home-ssd-switch/switch-<timestamp>-<nonce>/`，并 fsync。
3. **单个目录逐一原子替换**（Downloads 和 Documents 分开、独立执行，任一失败不牵连另一个）：
   - `os.rename(~/Documents, ~/Documents.orca-ssd-retained-<ts>-<nonce>)`——**这就是可回滚的备份，不是删除**。
   - 对 retained 目录逐项 `chmod` 去掉写权限（`& ~0o222`），并断言遍历后确无任何可写路径残留。
   - `os.symlink("/Volumes/Extreme SSD/UserHome/Documents", ~/Documents, target_is_directory=True)`。
   - **读回验证**：`os.readlink()` 拿到的字符串、以及 `Path("~/Documents").resolve(strict=True)` 解析出的真实路径，都必须与预期完全一致，否则立即触发自动回滚（见下）。
4. **替换后再验证一次**：再跑一次 `lsof +D` 确认 retained 目录（现在应该没人再往这条旧路径写）确实是零打开句柄；对新符号链接做一次功能性读测试（`ls`、`stat` 能正常解析、返回预期条目数）。
5. **完成标记**：写 `0600` 的 `SWITCHED.json`，记录事务 id、符号链接详情、retained 路径、回滚指令。
6. **中途失败自动回滚——及其明确不覆盖的窗口**：`os.rename` → `fsync` → chmod 只读 → `os.symlink` → 读回验证这一序列中，只要 Python 进程仍存活并抛出异常，`except` 块就会自动执行"若符号链接已建且与预期完全一致才 unlink，把 retained 目录恢复可写并改名回原路径，再重建一次清单与原始状态比对一致后才宣告成功"，区分 `failed-rolled-back`（回滚成功）与 `failed-rollback-incomplete`（回滚本身也失败，需要人工介入）两种终态并分别报告。

   **但必须如实声明一个该机制结构性无法覆盖的窗口**：在 `os.rename(源→retained)` 执行完毕、`os.symlink(目标→源)` 尚未执行完毕之间，**`~/Documents`（或 `~/Downloads`）这个路径本身在文件系统里完全不存在**——既不是目录也不是符号链接。如果在这个窗口内发生进程被 `kill -9`、系统 OOM 杀掉进程、或者真实断电/内核崩溃，上面的自动回滚**不会运行**，因为它依赖 Python 进程本身继续存活去执行 `except` 块。此时原目录已被安全地改名保存在 retained 路径下（**没有任何真实数据丢失**），但用户会看到该路径字面上"不存在"，而不是"能用"或"明确报错指向已知恢复流程"。

   在这个精确窗口内，两条既有的恢复路径都不适用：`switch --execute` 的预检要求所有待处理源路径的状态必须整齐划一地是"目录"或整齐划一地是"符号链接"，遇到"缺失"会直接判定为 `partial or unexpected source layout` 并拒绝重跑；`rollback` 子命令依赖 `SWITCHED.json`，而该文件只在两个目录**都**完成替换后才写出，在这个崩溃窗口内它还不存在，`rollback` 同样无法使用。

   **本设计要求为此新增一个 `heal` 子命令**，专门识别并处理这个窗口：
   - 触发条件：目标路径（如 `~/Documents`）在文件系统层面完全不存在，**同时**存在一个与 `PREIMAGE.json` 记录的 nonce 匹配的 `retained` 目录，**同时**不存在对应的 `SWITCHED.json`（即"改名已做，链接未建"这一特征组合）。
   - 行为：只读校验 retained 目录内容清单与 `PREIMAGE.json` 中记录的预期一致后，把该 retained 目录改名回原路径（`os.rename(retained → 原路径)`），使系统恢复到"Phase B 尚未开始"的状态，不尝试直接把中断的操作补完成符号链接（补建链接是一次新的、完整的 Phase B 尝试，而不是"续做一半"）。
   - 幂等与安全性：`heal` 本身只做一次原子改名，不涉及复制或删除，与其余子命令共享同一套四项全局规则前置检查与事务日志约定；重复调用在目标路径已恢复为目录后应识别为"无需处理"并安全退出，不报错。
   - 这一子命令与本设计其余部分一样，属于**设计规格**而非已实现代码，需在真正编写 `switch_user_home_folder_to_ssd.py` 时一并实现并纳入测试用例（专门构造"改名后、建链前"杀进程的测试场景），不能只在文档里承诺。

   经过以上明确声明与 `heal` 子命令的补充，本设计对"迁移过程中任意时刻中断"的保证被精确为：**任何中断都不会导致真实数据丢失（内容始终完整存在于 retained 目录或原目录中）**，但**不承诺**每一种中断窗口都能被同一个自动化命令一步恢复——`heal` 就是为了把"需要人工介入的窗口"从"无脚本化路径、只能靠用户自行 `mv`"缩小到"一个专门设计、经过测试的只读优先恢复命令"。
7. **独立的显式 `rollback` 子命令**：接受一个 `SWITCHED.json` 标记路径，独立于自动回滚之外，可在切换完成后的任意时间手动发起——重新校验符号链接仍是预期状态、unlink、恢复 retained 目录可写、改名回原路径、重新校验内容一致——同样具备失败时的再补偿逻辑。
8. **所有写入动作都挂在 `--execute` 开关后**；不带该开关时脚本只跑只读预检并打印"将会做什么"，不产生任何实际变更（对应第 5 节授权点 2 的"只读预检先单独跑一次"）。`heal` 与 `rollback` 同样遵循这一约定，不带 `--execute` 时只报告检测到的状态和将要执行的恢复动作，不实际改动。

### 3.3 retained 备份的保留期与删除条件

- retained 目录（`~/Downloads.orca-dh-work-broken-retained-*`、`~/Downloads.orca-ssd-retained-*`、`~/Documents.orca-ssd-retained-*`）在对应阶段完成后**保持只读、原样保留**，不设自动清理定时任务，不在任何脚本代码路径里出现自动删除逻辑。
- 建议最短保留期：**至少一个完整工作日**的正常使用观察 + **至少一次** logout/login 与 reboot 存活测试（专门用于验证第 4 节 c 提到的 iCloud Drive 符号链接重建风险没有发生），且用户对第 4 节 a 列出的关键应用（Safari 下载、Chrome 下载、Mail 附件保存、至少一个常用沙盒 App 的文件选择器）逐一手动验证过可正常访问 Downloads/Documents 后，才具备"可以考虑删除"的资格。
- **即使满足上述条件，删除动作也必须是用户后续单独、显式提出的新请求**（对照仓库 `COMPLETION-BACKLOG-2026-08-16.md` §4 中 17 个 `*rollback-backup*` 目录被保留直到用户明确授权删除的先例）——本设计与其配套脚本都不包含任何自动删除 retained 备份的代码路径，这是刻意的设计决定，不是遗漏。`~/Downloads.orca-dh-work-broken-retained-*` 额外受第 5 节授权点 0 的处置决定约束：若用户选择 (b) 另立专项恢复任务，该目录（及其记录的原符号链接目标字符串）在那个独立任务结束前不得删除。

## 4. macOS 特有陷阱的具体应对

### a) 沙盒 App / TCC 对符号链接的处理

沙盒应用（尤其是那些用 `com.apple.security.files.downloads.read-write` 这类 entitlement 的 App）内部对"Downloads"这个字面位置有专门的容器级符号链接特殊处理逻辑，替换成自定义符号链接**不保证**走同一条被测试过的代码路径，真实报告显示可能出现"要求重新对真实目标路径授权""每次启动重新弹权限提示"等情况。

**本设计的应对**：不追求"让所有沙盒应用都透明识别新符号链接"——这超出本设计范围，且没有系统性解法。应对方式是把它变成 Phase B 验证阶段的一个**已知成本清单**而非阻断项：迁移完成后，用户手动对日常使用的几个关键 App（至少含一个下载类、一个附件保存类、一个文件选择器打开 Downloads/Documents 的沙盒 App）各做一次实测，预期部分 App 需要重新走一次系统设置里的权限授权，这是**一次性成本**，写入验证清单，不阻塞迁移本身完成，但必须在第 5 节授权点里对用户说清楚"迁移后大概率要手动重新点几次权限确认"这件事。

### b) Spotlight 索引

审计已确认源位置（内置盘 Data 卷）和目标位置（Extreme SSD）当前都开启了 Spotlight 索引（`mdutil -s` 均返回 `Indexing enabled`）。**应对**：不需要特殊处理，Phase B 完成后内容天然会被索引；如果用户需要立即生效可选做一次 `mdimport` 触发式重索引，这是可选的、非阻塞的收尾动作，不纳入必须步骤。

### c) Time Machine 不会跟随符号链接备份目标内容

审计确认这台机器**当前没有配置任何 Time Machine 目的地**（`tmutil destinationinfo` 返回无目的地），所以"迁移导致 Documents 内容脱离现有备份覆盖"这件事**今天不成立**——因为今天本来就没有备份覆盖。但这是一个必须向前看的缺口：**本设计明确声明不在范围内处理**，理由是"建立 Time Machine/独立备份策略"是一个与"把文件夹搬到哪个盘"正交的独立任务，不应该被塞进本次迁移设计里一并解决。但必须写清楚残余风险：一旦用户以后配置 Time Machine 只对内置盘做备份，Downloads/Documents 迁移后将**只备份到一个悬空符号链接**，真实内容（含 Documents 里的合同、密钥文件）不会被 Time Machine 覆盖到——这一点连同"应该把 Extreme SSD 本身也纳入某种独立备份策略"作为**明确的后续待办**写入第 6 节风险清单（R 中体现），不由本设计代为解决。

### d) 浏览器/App 对下载路径的硬编码或缓存

已有直接证据（Safari，Catalina 时代但机制推断在当前系统仍可能存在）：部分 App 在启动/选择时读取并**缓存**一次 Downloads 绝对路径，而不是每次都重新解析符号链接，导致符号链接切换后该 App 的下载功能失效，需要重新在其偏好设置里"重选"一次目标目录才能恢复，且**重启后又失效**（表现为反复出现的成本，不是一次性的）。

**本设应对**：这是 Apple/第三方 App 自身实现的限制，不是本次迁移脚本能从底层修复的问题，**明确声明不做修复，只做验证与告知**——Phase B 完成后必须实测 Safari 下载一次并观察重启后是否复现该已知 bug；如果复现，把这个成本原样告知用户，由用户决定是"接受偶尔要重新点一下 Safari 偏好设置"这个持续性小成本，还是对 Safari 单独做例外处理（例如仅让 Safari 继续下载到内置盘上的某个位置，不强求它也走 SSD）。这个决策点不阻塞整体迁移是否完成，但要作为验证清单的一项写清楚结果。

### e) SSD 是可拔插移动硬盘——是否会重演当前 Downloads 的坏链接问题；以及哨兵脚本需要检测什么

**明确回答：会，且这不只是"拔出"这一种触发方式。** 一旦 Extreme SSD 被拔出，`~/Downloads` 和 `~/Documents` 会立即变成悬空符号链接，这一点已经过终端层面的直接验证：对当前处于断链状态的 `~/Downloads` 执行 `ls ~/Downloads/` 返回明确的 `No such file or directory`，`Path("~/Downloads").resolve(strict=True)` 抛出 `FileNotFoundError`——这是一个**清晰的错误**，而不是"看起来像空文件夹"。本设计据此**修正**早前草案中"Finder 会把它呈现为看起来是空文件夹"这一表述：这条描述本次调研只在终端层面验证过（结果是明确报错，不是"看起来空"），并未在 Finder 图形界面里实际操作复现；标准 macOS 对指向缺失目标的符号链接/替身，Finder 通常给出的是"原身...无法找到"这类明确弹窗提示，而不是静默呈现为空文件夹——如果这条关于 Finder 具体呈现方式的描述以后需要在设计中被引用为事实依据，应当先在 Finder GUI 里实际操作一次复现（例如临时拔出 SSD 后双击 Dock/Finder 侧栏里的 Downloads）取得截图或明确的操作步骤记录，而不是延续未经证实的转述。

这不改变本节要处理的真正风险：**无论错误呈现形式是终端报错还是 Finder 弹窗，用户仍然可能在没有充分理解"SSD 未挂载"这个根因的情况下，凭直觉做出错误的"恢复"操作**（例如看到 Documents 报错就手动新建一个同名空目录，这会导致 SSD 重新插回后符号链接与这个新建目录冲突）——这正是本设计仍然坚持要有主动告警机制的原因，理由不因"是报错还是看似空文件夹"这一描述细节的修正而改变。

**为什么仍然值得做（相对于"干脆不迁移"）**：Extreme SSD 与随意插拔的移动盘不同——它是当前 Claude Code/Orca 本身正在运行所在的工作盘，长期挂载；它"基本保持在线"的可靠性已经被 19 个现存生产符号链接（`.claude`、`.codex` 等）间接验证——如果这块盘真的频繁意外断开，这些已有符号链接早该天天出问题，而目前没有此类报告。这是经验性的、非 100% 的保证，需要如实告知用户，而不是包装成"没有风险"。

**把这个风险降到可接受、而非消除**——本设计**纳入**以下降级/告警机制作为 Phase B 完成后的必选组成部分（不是可选后续）：

1. **只读哨兵脚本 + LaunchAgent，检测两类不同的故障，而不只是"能否解析"**：每次登录/唤醒时对 `~/Downloads`、`~/Documents` 各做两项独立检查：
   - **检查一（SSD 不在线 / 悬空链接）**：`Path.resolve(strict=True)` 是否成功。失败即代表 SSD 未挂载或目标已不存在，对应第 4 节 e 描述的"拔出"场景。
   - **检查二（符号链接本体被替换）**：`os.path.islink(path)` 是否仍为真，且 `os.readlink(path)` 读出的字符串是否仍然精确等于预期的 SSD 路径（`/Volumes/Extreme SSD/UserHome/Documents` 或 `Downloads`）。这一项专门针对第 6 节 R4 描述的场景——iCloud Drive（或其他系统机制）把符号链接静默替换成一个全新的、真实的空目录：这种情况下路径**仍然能被 `resolve(strict=True)` 成功解析**（因为它现在指向一个真实存在的空目录），检查一完全无法发现这个问题，必须靠检查二的"是否还是符号链接、指向是否仍正确"来捕捉。
   
   任一检查失败，都立即通过 `osascript -e 'display notification ...'`（或系统通知中心）主动弹出告警，且告警文案区分两种情况（"SSD 未挂载，Downloads/Documents 当前不可访问" vs "检测到 Documents 已不再是指向 SSD 的符号链接，可能被系统重建，请勿手动写入此目录，需要人工核查"）——这是直接针对"用户误以为文件夹真的空了"以及"用户误判 R4 已经安全、实则被静默替换"这两个具体历史/研究提示的故障模式设计的对治手段，不是空泛的"要有降级机制"这句话。这个哨兵**只读、不做任何数据操作**，风险极低，纳入本设计范围。
2. **明确不做的事**：不实现"SSD 不在时自动切回某个本地副本"这类自动 failover，也不实现"检测到符号链接被替换后自动删除新目录、自动重建符号链接"这类自动修复。理由：这会引入数据分叉或误删刚被系统写入的新目录——SSD 和本地同时存在两份、用户搞不清哪份是当前活跃版本，比"文件夹暂时不可见"危险得多。设计原则是：**宁可明确失败并告警，也不要静默切换或静默自动修复**；检查二发现异常后的正确后续动作是人工核查 + 视情况走 3.2 节的 `rollback` 子命令，而不是哨兵自己动手。

### f) 是否需要"SSD 不在时的降级/告警机制"——结论

**需要，且已纳入本设计范围**，即上面 e) 中同时覆盖"路径不可解析"与"符号链接本体被替换"两类故障的只读哨兵通知脚本，作为 Phase B 完成后的必选交付物之一，而非事后可选项。因为该哨兵现在持续常驻运行（不是一次性检查），它同时也把第 6 节 R4 原本只依赖"一次 logout/login + 一次 reboot 存活测试"的验证方式，升级为对该风险的**持续性**监测，能够捕捉到并非在第一次登录就触发的、更罕见或延迟出现的重建行为。

## 5. 执行授权边界

**本设计文档本身不授权任何实际执行。** 复制、改名、建符号链接等一切写操作，都必须等到对应授权点被用户显式批准后才能运行；任何脚本在没有拿到 `--execute` 且没有对应人工批准记录的情况下，只允许跑只读预检。建议的分阶段授权点如下：

- **授权点 0（阻断性，最先）**：用户对 dh-work 历史下载内容的处置方式做出三选一的明确决定——(a) 已确认有其他备份/无需找回，可放弃；(b) 希望另立专门任务尝试恢复，本次迁移设计不动 Downloads，只先做 Documents；(c) 明确知晓"极可能已永久丢失"仍要求继续、放弃恢复、直接在新位置起一个空的 SSD Downloads。**在此决定之前，不得对 `~/Downloads`（包括当前那个坏符号链接本身）做任何改动，包括第 3.0.5 节的 Phase A0。**
- **授权点 1**：用户完成 1.2 节要求的 iCloud Drive GUI 人工确认，并明确表示知晓"iCloud Drive 总开关本身可能导致 Documents 符号链接被系统重建"这条未 100% 权威确认的风险后，仍同意继续 Documents 迁移。
- **授权点 2**：单独跑一次 Phase A0/A/B 脚本的**只读预检模式**（不带 `--execute`），把四项全局规则检查（加密/解锁/卷标识/所有权）+ 空间余量 + idle gate 的结果原样呈现给用户，由用户确认预检结果符合预期。
- **授权点 3**：批准执行 **Phase A0（仅 Downloads，退休现有断链）** 与 **Phase A（仅复制到 SSD staging，原目录完全不动，本质无损）**。
- **授权点 4**：Phase A 完成后，用户独立审阅 manifest 校验报告（不是脚本自称"成功"就直接放行，而是看具体的哈希/容差比对结果），确认无误后再批准执行 **Phase B**（真正的原子替换）。同时确认已知悉第 3.2 节第 6 点所述的"改名与建链之间"崩溃窗口及 `heal` 子命令的存在与用法。
- **授权点 5（建议但不强制立即执行）**：完成至少一个工作日的正常使用观察 + 一次 logout/login + 一次 reboot 存活测试、以及第 4 节 a 的应用验证清单后，再决定是否部署 4(e) 提到的、覆盖"不可解析"与"符号链接被替换"两类检测的哨兵告警 LaunchAgent 作为常驻服务。
- **授权点 6**：任何"删除 retained 备份目录（含 Phase A0 退休的旧 Downloads 断链）"的请求，必须是用户后续独立、重新提出的新指令，本设计和配套脚本都不包含自动删除路径。

## 6. 风险清单

**R1（数据丢失风险——复制期间源被并发写入）**：若 Phase A 复制过程中恰好有新文件写入源目录（例如浏览器正在下载），可能导致遗漏。缓解：idle gate（`lsof` + `.download`/`.crdownload`/`.part` 扫描）+ 复制前后源目录 manifest 强制逐项相等，不相等则整个 Phase A 判失败，不得进入 Phase B。

**R2（数据丢失风险——dh-work 内容已事实性永久丢失）**：这是本次迁移设计**发现但无法逆转**的既成风险，不是本次迁移新引入的——`dh-work.sparseimage` 缺失且遍历本机所有可达位置未找到，其中可能存在的历史下载文件极可能已永久不可寻回。这正是授权点 0 必须阻断执行、由人工先做处置决定的原因；3.0.5 节的 Phase A0 确保即使决定放弃恢复，指向该丢失卷的最后一条线索（旧符号链接及其目标字符串）仍会被完整保留而不是被删除。

**R3（SSD 拔出/断连导致 Downloads/Documents 表现为空——复现 dh-work 式故障）**：详见第 4 节 e。这是符号链接方案的结构性代价，无法被完全消除，只能通过 4(e) 升级后的只读哨兵告警机制（同时检测"能否解析"与"是否仍是指向正确目标的符号链接"）把它从"用户会误以为丢了数据"降级为"用户会立刻被告知盘不在线"。

**R4（iCloud Drive 反复覆盖 Documents 符号链接）**：研究证据表明这是最独特、最难对付的一类风险——即使当前 GUI 确认"桌面与文稿"同步已关闭，只要 iCloud Drive 总开关开着，仍有真实可能性使系统在下次登录/重启时把 `~/Documents` 符号链接静默替换回一个全新的本地空目录。这不会造成真实数据丢失（SSD 上的内容仍在），但极易让用户误判为"数据丢了"进而做出错误的手动"恢复"操作，反而引发真正的数据损坏。**需要特别注意**：这种被替换后的路径仍然是一个可以正常 `resolve` 的真实目录，单纯检测"路径能否解析"的哨兵完全无法发现它——必须依赖第 4 节 e 检查二（`islink` + `readlink` 比对）才能捕捉。缓解：Phase B 后必须做至少一次 logout/login 和一次 reboot 的存活测试，并从 Phase B 完成起持续接受该升级哨兵的常驻监测（而不只是一次性验证）；一旦任何一次检测（无论是首次存活测试还是后续常驻监测）观察到符号链接被系统重建，**立即整体回滚 Documents**（走 3.2 步骤 7 的显式 `rollback` 子命令，回滚前先确认 SSD 上的原内容仍完整无损），不建议二次尝试（Apple 是在主动对抗这个配置，重试大概率仍会被覆盖），并把"Documents 迁移"标记为在这台机器上不可行，只保留 Downloads 迁移。

**R5（权限/ACL 损坏导致 Documents 被系统判定为"required by macOS"）**：研究中有真实案例显示 Documents 符号链接替换过程中出现 ACL `+` 标志阻止删除、最终系统报"required by macOS"错误的情况。缓解：整个流程绝不使用 `rm -rf`，只用 `os.rename` 做改名（不触碰 ACL 本身）；预检阶段先用只读的 `ls -le` 检查是否已存在异常 ACL，发现异常则该次迁移直接中止并升级为需要人工介入，不尝试脚本自动修复 ACL。

**R6（迁移过程中遭遇进程被杀/断电，路径短暂完全消失）**：详见 3.2 节第 6 点。`os.rename(源→retained)` 与 `os.symlink(目标→源)` 之间存在一个自动异常处理无法覆盖的窗口，在此窗口内被强制中断会导致目标路径（如 `~/Documents`）在文件系统中短暂完全不存在（不是目录也不是符号链接），且现有的 `switch --execute` 重跑与 `rollback` 子命令在这个精确窗口内都不适用。**没有真实数据丢失**（内容始终完好地存放在已改名的 retained 目录里），但需要新增的 `heal` 子命令（识别"源缺失 + retained 目录存在 + 无 SWITCHED.json"这一特征组合并把 retained 目录改名回原路径）来提供一条脚本化的恢复路径，避免用户唯一的出路是凭记忆手动执行一次未经审计的 `mv`。`heal` 子命令必须与其余子命令一样接受 `--execute` 门禁与全局四项规则检查约束，且需要在真正编写脚本时补充针对该崩溃窗口的专门测试用例。

**R7（凭证暴露的附带提示，非迁移本身引入的新风险）**：Documents 下两份文件名疑似 GCP service-account 密钥的 JSON 文件会随迁移一起被搬到 SSD——内容和暴露面不因换位置而改变，不构成迁移新增的风险。但顺带提醒：这类凭证长期放在 Documents 里本身是需要用户单独处理的安全隐患（尤其未来该目录可能被更多云同步/备份工具接触到），建议迁移完成后由用户单独决定是否需要旋转或迁移到更安全的密钥管理位置——不属于本次迁移范围，仅作提示。
