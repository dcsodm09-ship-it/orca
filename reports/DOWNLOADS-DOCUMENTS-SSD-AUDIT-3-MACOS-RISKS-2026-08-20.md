# Audit 3: macOS 特殊文件夹迁移风险调研

# macOS Symlinked Downloads/Documents — Research Findings (Sonoma/Sequoia, APFS, FileVault)

## Bottom line up front
Relocating `~/Downloads` via a plain `ln -s` symlink is technically possible and does work for many apps, but it is **not an Apple-supported configuration**, and the evidence below shows real, reproducible failure modes — including the exact "external volume unmounted → folder looks empty everywhere" failure this user is already experiencing. `~/Documents` (and `~/Desktop`) are materially worse candidates because macOS actively fights symlinks there due to iCloud Drive's Desktop & Documents management. No first-party Apple document endorses this technique for either folder.

---

## 1. App Sandbox / TCC and symlinked Downloads/Documents

**Sandboxed apps generally do not transparently follow a Downloads/Documents symlink to grant access — they need the *real* (resolved) path granted.**

- Apple's own sandbox container mechanics: inside an app's sandbox container, the "Downloads" entry is itself implemented as a symlink to the real Downloads directory, and access is governed by entitlements like `com.apple.security.files.downloads.read-write` plus `RedirectablePaths` in the container's plist — i.e., the sandbox already has special-cased symlink handling for the *stock* location. Swapping in your own symlink target isn't the same code path Apple tested. ([Apple Developer Forums — Downloads permission](https://developer.apple.com/forums/thread/731972), [com.apple.security.files.downloads.read-write — Apple Developer Documentation](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.files.downloads.read-write))
- Reported real-world consequence: if a nested/child path is itself a symlink, the sandbox does **not** implicitly extend permission to it — the app must obtain permission to the *real* target folder, which can mean extra prompts. ("If you want to list contents of a nested folder that is actually a symlink, this doesn't work — you have to grant permissions to the real folder.")
- A directly on-point MacRumors thread from a Sequoia (M4 Mac mini) user who put their **entire home folder** on an external (Thunderbolt, FileVault-encrypted) SSD reported that TCC-driven apps (Bartender 5, Shottr) **re-prompt for screen-recording/screen-picker permission on every boot/relaunch**, even after `tccutil reset`, manually re-granting in System Settings, and even with SIP disabled. Testing confirmed the same accounts had no issue when the home folder was on internal storage. The community's own conclusion/workaround was: **don't relocate the whole home folder or top-level special folders — instead symlink only large sub-folders from inside an internally-located home folder.** ([Persistent TCC Permission Prompts on External Home Folder Setup — MacRumors](https://forums.macrumors.com/threads/persistent-tcc-permission-prompts-on-external-home-folder-setup-bartender-shottr-etc.2458163/))
- Background on TCC's two parallel access mechanisms (useful context, not symlink-specific): TCC consent (`kTCCServiceSystemPolicyDownloadsFolder`, `...DocumentsFolder`, `...DesktopFolder`, checked against Full Disk Access first) vs. a separate, TCC-invisible kernel/sandbox layer using MACL extended attributes attached to a directory when the user picks it via an Open panel — these MACLs "take precedence over TCC's controls." Neither of Howard Oakley's (Eclectic Light Co.) detailed TCC-internals articles I could reach explicitly documents *how* either mechanism resolves a symlink vs. its target, so I could not find an authoritative first-party or expert statement nailing down the exact resolution algorithm — flagging this as **not conclusively sourced**, only inferable from the failure reports above. ([Explainer: Permissions, privacy and TCC](https://eclecticlight.co/2025/11/08/explainer-permissions-privacy-and-tcc/), [Privacy: How locations are protected](https://eclecticlight.co/2026/04/20/privacy-how-locations-are-protected/))
- Separately, a known (if narrower) macOS security-research finding: sandboxed apps following a symlink that leads *outside* their granted scope hit outright permission errors and must either have the symlink removed or be granted access to the real target explicitly — this is standard behavior developers must code around, not something transparent to the end user. ([A New Era of macOS Sandbox Escapes](https://jhftss.github.io/A-New-Era-of-macOS-Sandbox-Escapes/), [macOS Sandbox — HackTricks](https://hacktricks.wiki/en/macos-hardening/macos-security-and-privilege-escalation/macos-security-protections/macos-sandbox/index.html))

**Net effect for the user's symptom class ("app asks for Downloads access every time"):** this is a documented pattern, not a one-off — real users on current macOS report exactly this with external-volume home-folder/Downloads setups.

## 2. Spotlight, Time Machine, and the "volume unmounted → folder looks empty" risk

**This risk is not hypothetical — it is standard, expected Unix/macOS symlink behavior, confirmed by multiple independent sources, and it is exactly what has already happened to this user.**

- **Dangling symlink behavior:** when a symlink's target volume is unmounted, the link itself survives in the file system, but Finder "can still navigate to it and show it as though it exists, though there are no files in it" — i.e., a broken symlink typically renders as an *empty folder* rather than a clear error, which is the deceptive/dangerous part (nothing overtly signals "your data is inaccessible," it just looks empty). Terminal (`ls -l`) will show the stale target path after the `->` arrow even when unreachable. ([community discussion synthesis](https://forums.macrumors.com/threads/cannot-delete-symlink-from-root.2319400/), general symlink references)
- Apple Community confirms the general mechanism explicitly: "If you have a symbolic link from your home directory to a folder on the external drive... and that external drive becomes unmounted, that connection is temporarily broken" — every app reading through that path sees nothing. ([Ask MetaFilter: Downloads folder disappeared](https://ask.metafilter.com/386730/Mac-Downloads-folder-has-disappearedeven-in-Time-Machine-backups))
- **Time Machine explicitly does NOT follow symlinks to back up their target contents.** Direct Apple Community expert answer: *"TM will backup the links but not the files."* This means if `~/Downloads` or `~/Documents` is a symlink to an external volume, a Time Machine backup of your internal disk captures only the dangling pointer — **your actual files are backed up only if the external volume is separately, additionally configured and connected as its own Time Machine source at backup time.** This is a serious, easy-to-miss data-protection gap. ([Does Time Machine follow symbolic links? — Apple Community](https://discussions.apple.com/thread/7726175))
- Time Machine also cannot back up a drive that's connected indirectly (e.g., via a NAS/router USB port) — only drives directly attached (USB/Thunderbolt) are backed up, another relevant constraint if the external volume isn't always directly plugged into the Mac. (Same source as above.)
- Time Machine does **not** exclude Downloads by default — general folders are backed up unless manually excluded (only Trash/caches/certain system paths are default-excluded), so the exposure above is real for typical setups, not something Apple auto-mitigates. ([support.apple.com — Exclude files from a Time Machine backup](https://support.apple.com/en-ie/guide/mac-help/mh14037/15.0/mac/15.0))
- **Spotlight:** I could not find macOS-version-specific (Sonoma/Sequoia), symlink-specific authoritative documentation on how Spotlight indexes a folder reached only via a symlink to an external volume. What is well documented is the adjacent, general problem: Spotlight/mdworker indexing of *external volumes themselves* is flaky and support-thread-heavy (re-indexing needed, NTFS unsupported, index sometimes silently stops), and naturally an unmounted volume cannot be indexed or searched at all while disconnected — content under the dangling symlink simply won't appear in Spotlight results during that time. **Flagging this as inferred from adjacent evidence, not a directly-sourced Spotlight+symlink statement.** ([Spotlight not indexing external drive — Apple Community](https://discussions.apple.com/thread/252197427), [MacRumors — Spotlight not finding results on external HD](https://forums.macrumors.com/threads/spotlight-not-finding-results-on-external-hard-drive.2398668/))
- FileVault interaction (relevant since the user's setup involves FileVault): if the external volume is itself FileVault/APFS-encrypted, it **cannot be unlocked at boot time before a user logs in** — only the startup volume unlocks at the pre-boot screen. Community-documented consequence: home-folder-on-external-encrypted-volume setups can fail to be available in time at login, requiring workarounds like a secondary always-unlocked admin account, or third-party boot-unlock daemons (e.g., BootUnlock for APFS) that stash the passphrase in Keychain and unlock via a LaunchDaemon before the login window. This is an added moving part with its own failure modes. ([FileVault and volume encryption explained — Eclectic Light Co.](https://eclecticlight.co/2025/01/10/filevault-and-volume-encryption-explained/), [Encrypt external volume with home folder — Apple Community](https://discussions.apple.com/thread/252592784), [BootUnlock (GitHub)](https://github.com/openwall-com-au/BootUnlock))

## 3. Browsers/apps caching or hardcoding the Downloads path instead of re-resolving the symlink

**Confirmed for Safari specifically; Chrome is configurable per-profile but I could not find a definitive symlink-specific bug report for it.**

- Directly on point — an Apple Community thread from the Catalina era: a user symlinked `~/Downloads` to an SD card. Safari **stopped downloading entirely**, throwing an error. Diagnosis: re-selecting the (symlinked) folder in Safari's Preferences would make downloads work again *until Safari was quit and relaunched*, at which point it broke again — strongly indicating **Safari caches/resolves the Downloads path at launch/selection time rather than continuously re-resolving `~/Downloads` through the symlink**. Curiously, symlinking a *non-special* folder (e.g., Pictures) and pointing Safari at that worked fine after restart — implicating special-cased handling of the literal "Downloads" location, not symlinks generally. The thread closed without an Apple-confirmed fix, only the user's own workaround (point Safari at a differently-named symlinked folder instead of the literal Downloads symlink). ([Since Catalina Upgrade Safari won't download — Apple Community](https://discussions.apple.com/thread/250745827))
- General confirmation that Downloads-folder is app-configured, not systemically redirectable: "That's set in any app that downloads files. There's no global setting for that" — i.e., there is no OS-level hook that guarantees every app re-resolves a symlink identically; each app's own download-location logic governs behavior. ([Setting Downloads and Documents on external drives — MacRumors](https://forums.macrumors.com/threads/setting-downloads-and-documents-on-external-drives.2278114/))
- Chrome: Chrome's download location is a per-profile preference (`downloads.default_directory` internally) set via Settings → Downloads → Change, defaulting to the real `~/Downloads` path. I found practical how-tos for changing it, but **no specific report of a Chrome+symlinked-Downloads bug** comparable to the Safari case — flagging this as **not found**, not as "confirmed fine." Given Chrome resolves and stores an absolute path at selection time (same general pattern many apps use), the same class of staleness risk (a cached absolute path outliving a symlink swap) is architecturally plausible but unconfirmed by a citable source.
- Mail.app: attachments save location is a separate, independently configurable Mail > Settings > General preference (defaults to Downloads but can point elsewhere) — meaning Mail is yet another app with its own path state that would need to be checked/reconfigured, rather than automatically inheriting a Downloads-symlink swap. ([View, save, or delete attachments in Mail — Apple Support](https://support.apple.com/guide/mail/view-save-or-delete-email-attachments-mlhlp1123/mac))
- Net pattern confirmed across sources: **there is no single OS-level switch that relocates "the Downloads folder" for all software.** Symlinking `~/Downloads` handles apps that re-resolve `NSHomeDirectory()/Downloads` (or literally re-read the path) on each use, but any app that snapshots/caches an absolute path (demonstrated for Safari) needs to be individually re-pointed after the swap, and needs re-checking after macOS/app updates.

## 4. iCloud Drive "Desktop & Documents" sync vs. a symlinked Documents folder

**Documents is fundamentally incompatible with symlinking once iCloud Drive is involved — this is the strongest, most consistently corroborated finding in this research.**

- Multiple independent threads across Catalina through Sequoia describe the *same* mechanism: **macOS actively replaces/recreates the Desktop and Documents folders as real local folders on every login**, overwriting any symlink placed there, specifically *because* Documents/Desktop became "special," iCloud-Drive-managed locations starting in Catalina. One Apple Developer Forums thread title is literally "Catalina Overwriting Symlinked Document Folders," and a community reply states plainly: **"Apple has never supported symbolic links for any folder having any special meaning to the system."** ([Catalina Overwriting Symlinked Document Folders — Apple Developer Forums](https://developer.apple.com/forums/thread/122804))
- This is confirmed as still true through Sequoia in current searches — the trigger is having **iCloud Drive enabled at all** (even without Desktop & Documents actively turned on): "Selecting iCloud Drive... causes symlinks to not persist after logoff/login or rebooting. Disabling iCloud Drive will prevent the system from resetting symbolic links." So the risk is forward-looking exactly as the user framed it: **it doesn't matter that iCloud Desktop/Documents sync isn't active today** — merely having iCloud Drive itself turned on is enough to make macOS fight a Documents symlink; actually enabling Desktop & Documents sync would only compound this.
- A separate Apple Community thread ("Replace Documents folder with a symlink?") documents a user's Documents folder becoming outright **corrupted** during a symlink-replacement attempt — ACL "+" flags blocking deletion, `rm -rf` failing with "Operation not permitted," and macOS eventually reporting the folder as "required by macOS" after permissions got mangled during troubleshooting. The Apple Community consensus response there: **moving the entire user account/home folder to the external volume is more reliable than trying to symlink just Documents.** ([Replace Documents folder with a symlink? — Apple Community](https://discussions.apple.com/thread/254488814))
- On the sync mechanism itself: when Desktop & Documents *is* turned on, Apple's engineering approach is not "make Documents a symlink to iCloud" — instead, files are physically relocated within the same local APFS volume to a different internal location, and the visible `~/Documents` becomes an iCloud-Drive-managed junction Apple itself controls (per Eclectic Light Co.'s firmlinks/iCloud research), which is architecturally the opposite of pointing it at an external volume. Apple's own support article on the feature doesn't discuss external volumes at all, but does say plainly: "If you use a feature from another cloud provider that syncs or manages your Desktop and Documents folders, you need to turn it off" — i.e., Apple treats any *other* redirection of these folders as something that must be disabled first, not something compatible with iCloud sync. ([Add your Desktop and Documents files to iCloud Drive — Apple Support](https://support.apple.com/en-us/109344))
- Known duplicate-data failure mode when the feature interacts with multiple Macs/relocated folders: users report `Documents - [MacName]`-style duplicate folders appearing inside iCloud Documents — consistent with "conflict/duplicate," one of the exact risks the user asked about.

**Conclusion for point 4:** If Desktop & Documents iCloud sync is ever turned on with Documents as an external symlink, expect one of: the symlink being silently replaced by a fresh local folder (files apparently "disappearing" from view even though the external copy still exists at its real path), permission/ACL corruption on the Documents folder, or duplicate-named folders — not silent perfect compatibility.

## 5. Safest, most standard, most reversible community/Apple-documented procedure

**Key finding: there is no Apple-endorsed procedure for symlinking these specific special folders. Every authoritative and community source converges on the same alternative hierarchy, from safest to riskiest:**

1. **Apple's actual recommendation is: don't relocate Documents/Desktop/Downloads at all.** Store large content in-place and instead offload big *libraries* (Photos, Music, iMovie, Final Cut) to external storage using each app's own built-in relocation feature — Apple's official guidance is explicit that "moving your Documents folder will be problematic and unreliable" and that the supported pattern is per-app library relocation, not folder-level symlinking. ([synthesis of Apple Community guidance](https://discussions.apple.com/thread/254854380), [MacRumors thread](https://forums.macrumors.com/threads/setting-downloads-and-documents-on-external-drives.2278114/))
2. **If you must relocate the whole home directory** (the more "official" of the unofficial paths, and the one several Apple Community experts recommended over symlinking individual special folders): use **System Settings → Users & Groups → [account] → Advanced Options → Home directory → Choose**, point it at a folder on the target volume, restart, then **manually copy** old contents over (macOS does *not* auto-move data for you — this is a deliberate two-step process, not automatic). AppleInsider's Ventura how-to documents these exact steps and pairs them with explicit Apple-community-sourced warnings:
   - "The connection to that volume must be perfectly reliable — meaning both the drive and the cable" because the home folder is "an integral part of macOS."
   - "If the connection isn't perfectly reliable, and the volume containing the home folder disappears even for a second, strange and undefined behavior may result. You could even lose data."
   - External/USB is slower than internal SSD, and mount-timing delays can cause login-time failures.
   - Community add-on warning specific to Sonoma+: "If you move your home folder and your external SSD is not available (or not available in time) when you boot, your Mac may not actually boot."
   ([How to move your Home directory in macOS Ventura — AppleInsider](https://appleinsider.com/inside/macos-ventura/tips/how-to-move-your-home-directory-in-macos-ventura), [best way to move Home folder — Apple Community](https://discussions.apple.com/thread/255135288))
3. **If you symlink anyway, community best practice (repeated across several threads) is: keep the folder itself, and its contents, on the internal (or reliably-always-mounted) volume, and only symlink specific *sub*-folders you don't mind risking** — never the top-level special folder itself, and never Documents/Desktop once iCloud Drive is enabled. One long-time practitioner's report: "I've been doing this with my Downloads and Pictures folder for years... it simply works for all applications" — but this is Downloads/Pictures (non-iCloud-managed, non-TCC-hostile in their case), explicitly not Documents/Desktop.
4. **Reversibility procedure, if attempted:** the standard, low-risk sequence documented across sources is (a) confirm the external volume is mounted and stable, (b) `cp -a` (or `ditto`, which preserves APFS metadata/xattrs/ACLs better) the real folder contents to the new volume location, (c) rename or remove the original folder (expect ACL "+" flags requiring `chmod -N` first, per the Apple Community ACL-corruption thread), (d) `ln -s /Volumes/YourDrive/Downloads ~/Downloads`, (e) verify. Reversing is simply: remove the symlink, `ditto`/`cp -a` the data back, restore the original folder. This is exactly the "safe" shape of procedure implied by the tools and steps forum users converge on (e.g., "Symbolic Linker" GUI utility on GitHub, or manual Terminal steps) — but note this is **community best-practice, not an Apple-published procedure**; I could not locate an Apple support document that describes or sanctions this workflow for Downloads/Documents specifically.
5. Given the user's stated situation is already a broken symlink, the lowest-risk immediate remediation per the sourced Time-Machine/dangling-symlink behavior above is: reconnect (or permanently retire) the target external volume first, confirm real data integrity there (not just Finder's "empty folder" illusion), and only then decide whether to keep the symlink (with a directly-attached, always-on volume and its own independent Time Machine/backup coverage) or fold the data back onto internal storage and remove the symlink — because as documented, Time Machine backing up the Mac's internal disk was **not** capturing the real contents through that broken link in the first place.

## Explicit gaps (flagged, not guessed)
- No first-party Apple document was found stating precisely *how* TCC's consent layer resolves a symlink to a relocated Downloads/Documents (path-string vs. realpath/inode-based check) — only strong circumstantial/behavioral evidence from bug reports.
- No citable Chrome-specific bug report of "Chrome hardcodes/mis-resolves a symlinked Downloads folder" was found (only the well-documented Safari case); Chrome's per-profile absolute-path storage makes the same failure mode architecturally plausible but unconfirmed.
- No macOS-Sonoma/Sequoia-specific, symlink-specific Spotlight indexing statement was found; the conclusion here is inferred from (a) general external-volume Spotlight flakiness reports and (b) the undisputed fact that content behind an unmounted-volume symlink cannot be indexed while disconnected.
