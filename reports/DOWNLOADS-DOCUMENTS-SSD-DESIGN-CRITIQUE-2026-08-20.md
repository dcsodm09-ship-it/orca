# 对抗性复核意见（数据安全视角）

## Adversarial review — Downloads/Documents → SSD symlink migration design

I verified this design against the live machine (read-only: `ls`/`stat`/`diskutil`/`defaults`/`mount`/`tmutil`/`launchctl`, plus reading the actual `migrate_android_heavy_data_to_ssd.py` / `switch_android_heavy_data_to_ssd.py` scripts it proposes to reuse). Almost every factual claim in the doc checked out exactly — Downloads is indeed the described dangling symlink to a missing `dh-work.sparseimage` (the LaunchAgent plist matches verbatim, and it's currently loaded but not running, PID `-`); Documents is a real 197MB/12-entry directory with the exact file types and two GCP-style key filenames described; SSD is FileVault-encrypted/unlocked/owners-enabled with the UUID the existing Android script already hardcodes; Time Machine has no destination; the `FXICloudDriveDesktop/Documents/Enabled` = `0/0/1` values are exact; the internal container is genuinely ~92% full; the reused Android scripts really do full-content SHA-256 (not count-only) verification with fsync'd 0600 journal files and dual rollback paths. The §2 Apple-entitlement distinction is also correct — the backlog's `BLOCKED_APPLE_ENTITLEMENT` items are genuinely about an internal EndpointSecurity/XPC engine, unrelated to userland `os.symlink`.

Given that strong baseline, here are the concrete gaps, ranked by real data-loss/inaccessibility risk:

### 1. (High) The "kill/crash/power-loss halfway" case is not actually fully covered, despite the doc's claim
§3.2 step 6 says "任何一步出错，自动执行...回滚." That's true for Python-level exceptions, but I read the actual `switch()` implementation: the per-pair sequence is `os.rename(source→retained)` → `fsync` → chmod read-only → `os.symlink(target→source)` → `fsync`. Between the rename and the symlink, `~/Documents` (or `~/Downloads`) **does not exist at all** — not as a directory, not as a symlink. The automatic-rollback `except BaseException` block only runs inside the still-alive Python process; a `kill -9`, OOM-kill, or literal power loss in that window skips it entirely.
Worse: on the next run, neither recovery path helps. `switch --execute` requires source states to be uniformly `"directory"` or uniformly `"symlink"` — "missing" hits `raise SwitchError("partial or unexpected source layout")`. `rollback` requires a `SWITCHED.json`, which is only written *after* both pairs are fully switched — so in this exact crash window it doesn't exist yet either. Net result: the user is stuck with a literally-missing `~/Documents` path and no scripted way out; the fix is a manual `mv ~/Documents.orca-ssd-retained-<ts>-<nonce> ~/Documents`.
No real data is destroyed (the retained directory is intact), but this directly contradicts the "safe if interrupted halfway" framing you asked me to check, and it's inherited unmodified from the Android script this design commits to reusing verbatim.
**Fix**: document this exact residual window explicitly (don't imply full auto-recovery from "any" interruption), and/or add a `heal`/`resume` subcommand that recognizes "source missing + an unconsumed `PREIMAGE.json` whose retained path exists" and offers the same rename-back recovery `rollback` does for the post-`SWITCHED.json` case.

### 2. (High) The one continuously-running safety net doesn't cover the design's own scariest risk
§4(e)/§6-R3's sentinel LaunchAgent is specified as: check whether `Path.resolve(strict=True)` succeeds, alert if not. That correctly catches "SSD unplugged → dangling symlink." It does **not** catch R4 — macOS silently replacing the `~/Documents` symlink with a brand-new real, empty directory — because a plain directory resolves just fine. The design spends its longest, most careful risk section (§1.2, §4-c-item-3, §6-R4) on exactly this failure mode, but the only automated guard it commits to deploying is structurally blind to it, and the mitigation for R4 as written ("do one logout/login + one reboot, then treat it as validated") can't rule out a rarer/delayed trigger condition either.
**Fix**: extend the sentinel to also assert `os.path.islink(path)` and that `os.readlink(path)` still equals the expected SSD path, alerting if the path exists but is no longer a symlink (or points somewhere unexpected) — not just "did resolve fail." This is a one-line addition that both closes the R4 blind spot and turns the one-shot soak test into standing protection against a trigger that might not fire on the very first login.

### 3. (Medium) The pre-existing broken Downloads symlink's disposal isn't carried into the audited pipeline
§1.1 states the intent clearly in prose ("先原样保留/改名备份，不删除"), but §3's mechanics (which explicitly reuse the Android scripts' `validate_source_layout()`) require the *source* to already be a plain directory — that check hard-fails on a symlink. There's no numbered "Phase A0" step in §3 for Downloads that renames the existing broken symlink aside with the same fsync'd/audited rigor as everything else. Left as unspecified prose, the actual retirement of that symlink risks being improvised outside the reviewed transaction machinery — and if anyone does it as a quick `rm ~/Downloads` instead of a preserving rename, that destroys the last on-disk breadcrumb (`/Volumes/dh-work/_mac_migrated/Users/www1adwawd/Downloads`) that the still-undecided, independent dh-work forensic-recovery effort (Authorization Point 0(b)) would need.
**Fix**: add an explicit "Phase A0 (Downloads only)" step to §3 that renames the current symlink to something like `~/Downloads.orca-dh-work-broken-retained-<ts>-<nonce>` via the same fsync'd/journaled convention, before `mkdir`-ing a fresh empty directory for Phase A to treat as source.

### 4. (Lower severity, but exactly the "asserted as fact" pattern you asked me to hunt for) The Finder-behavior claim in §4(e) is stated more confidently than it's actually substantiated
§4(e) says the "looks like an empty folder, not an explicit error" behavior is "本次调研亲眼验证过的、正在发生的真实故障模式，不是理论推测." I tested the live, currently-broken `~/Downloads` symlink directly (read-only): `ls ~/Downloads/` returns `No such file or directory`, and `Path.resolve(strict=True)` raises `FileNotFoundError`. That's a clear error, not silent-empty. I didn't drive Finder's GUI (kept this review read-only/non-interactive as instructed), but standard macOS Finder behavior for a symlink/alias to a missing target is typically an explicit "the original item... can't be found" alert, not a silently-empty view — which would contradict the doc's "looks empty" framing too. This doesn't change that the underlying risk (SSD unplugged → data inaccessible) is real and correctly flagged, and it doesn't weaken the case for fix #2's sentinel — but the specific evidentiary claim ("亲眼验证过") isn't backed by anything reproducible in the document, and should either be substantiated (actual Finder screenshot/repro steps) or softened.

### What's genuinely solid (say so plainly)
- Copy-then-verify-then-atomic-swap ordering is correct and, unlike a fresh design, is not theoretical — it's the same pattern already running in this repo's Android migration, and I confirmed the manifest-equality check really does per-file SHA-256 + xattrs + ACL + resource-fork digest + symlink-target-string comparison, not just counts, which specifically defeats the "USB disconnect silently truncates a large file" failure mode you asked about.
- The four global-rule preconditions (encrypted/unlocked/UUID-pinned/owners-enabled) are real, currently-passing, fail-closed gates in the actual code, not aspirational bullet points.
- The "retained backups are never auto-deleted, only by a later explicit user request" policy correctly cites a real precedent (`reports/COMPLETION-BACKLOG-2026-08-16.md` §4, 17 `*rollback-backup*` dirs, verified real).
- The §2 distinction from the `BLOCKED_APPLE_ENTITLEMENT` backlog items is accurate, not a rationalization — confirmed against the backlog's own text.
- It appropriately hedges the one genuinely unconfirmable claim (iCloud-Drive-total-switch symlink-rebuild risk) as unconfirmed research evidence requiring human GUI confirmation + explicit sign-off, rather than asserting it as fact — which is the correct posture and stands in useful contrast to finding #4.
