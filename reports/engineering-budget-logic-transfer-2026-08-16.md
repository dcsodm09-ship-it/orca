# 调研结论：《建设工程预算测算逻辑》能否迁移到完善orca

来源文档：`/Volumes/Extreme SSD/Orca/workspaces/工程量预算/工程预算/工程预算测算逻辑.md`（4361 行，
由 op5/Claude Opus max 与 solmax/Codex gpt-5.6-sol design 独立研究、交叉审查融合定稿）。

## 结论：不迁移造价公式本身，但治理方法论有高价值、可直接落地的迁移空间

这份文档讲的是建设工程造价体系（投资估算→设计概算→施工图预算→……→竣工决算），字面内容
（消耗量定额、综合单价、税率公式）对软件项目没有直接意义。但它的**元层面纪律**——如何让一个多来源、
多阶段、反复被复核的治理体系保持自洽、可追溯、不自相矛盾——和完善orca这几周暴露出的真实问题几乎
一一对应。全部 47 条候选模式的详细分析已按章节读完（一~五章 + 附录），本文只挑出直接命中已知缺陷、
且能低成本落地的部分。

## 三个已知缺陷 → 三条直接对症的迁移模式

今天这一轮工作过程中，恰好连续三次撞上同一类问题（详见本 session 各阶段报告），文档里刚好各有一条
现成的对应设计：

### 缺陷 1：候选报告自称"已通过"，被更晚的独立复核推翻

今天亲手发现并纠正了两处：`r2-run-identity-closure` 自称 27/27 通过，被两小时后的独立审计证伪为
20/20+2 BLOCKED、结论 NO-GO；`archive-provenance-normalization-closure` 标题写 GO，被同日晚些的
独立验收发现 3 个 P0 后仍未更正标题。

**对应模式（5.7.3 + 5.8）：仅凭已落库证据出具解释，禁止事后反推 + 孤儿结论检测（TRACE_ORPHAN）**
> 解释 API 硬性约束"解释结果必须来自已落库的追溯图，不允许由报表端或语言模型反推公式"；每个非零
> 结果必须可达至少一个业务输入 + 一个依据快照，否则报错。

落到完善orca：任何候选包的"已通过/已验收"结论，其依据必须严格来自已持久化的评审记录（具体
diff/日志/复核意见文件引用），禁止靠印象补写一个听起来合理的理由；找不到可复现证据链的"已修复"声明
视为孤儿结论，直接阻断，不默认相信自述文字。这是本次调研里价值最高的一条——严格执行，很多本次
碰到的矛盾根本不会等到下一轮复核才暴露。

### 缺陷 2：已装运行态与任何源码分支哈希都不一致，无法追溯版本

已经在多份既有报告里反复出现（记忆守护进程、Prime Agent 早期版本等）。

**对应模式（5.0.1 P4 + 5.2.3）：可复现三元组 + 不可变运行记录**
> `(input_hash, config_hash, engine_version)` 三元组相同则输出必须逐分位一致；`calc_run`
> 成功运行后不可变，重算生成新 `run_id`，历史 run 永不覆盖。

落到完善orca：每次已装/已发布运行态都应绑定一个不可变的 `(源码 commit 哈希, 配置/规则包版本,
部署时间戳)` 三元组快照独立存档；任何"重算/复核"生成新记录而不是覆盖旧记录。这条不需要发明新东西，
只是把现有 SHA-256 哈希核对的习惯升级成强制、结构化、可查询的记录。

### 缺陷 3：矛盾发现后，没有统一的差异归因，只能"谁的结论更晚谁作数"

**对应模式（5.7.4）：结构化归因对比 run_diff**
> 两次运行的差异结构化归为量差/价差/费率差/口径差/版本差/新增删除项六类，按影响排序。

落到完善orca：当两路独立复核结论不一致，或某候选先"通过"后被推翻，应输出结构化差异归因——是
范围不同（看的 diff/commit 不同）、方法不同（测试覆盖不同）、证据不同（后者查了前者没查的东西）、
版本不同（复核的不是同一份代码），还是纯粹的新发现——而不是简单地"以晚为准"。

## 另外 5 条值得留意但优先级稍低

- **必填元数据缺失即强制降级为 DRAFT_ONLY 水印**（5.5.2 + 5.9）：候选报告缺关键字段（复核者、
  commit哈希、复现步骤）时强制打草稿水印，禁止被当成正式成果。今天手写的三份"纠错说明"本质上就是
  在事后补这个水印——如果这条规则一开始就存在，那两处矛盾可能在写报告的当下就会被自动拦下。
- **数据层结构性互斥**（5.0.1 P5）：一个候选在任一时刻只能有一个"权威状态"字段，而不是允许多份
  报告各自独立宣称"已通过"、只能靠人工比对才发现矛盾。
- **显式编号不变式清单 + 组合式发布门槛**（5.9，类似造价方案的 I1~I15）：把双复核、P0/P1 阻断、
  容量新鲜度等散落的政策文字，收敛成一份可机械校验的编号清单。
- **分层权威 + 覆盖必须留痕**（5.0.1 P6 + 5.7.4 override_event）：CLAUDE.md 里"更具体规则可加严
  不可放松"已经是这个原则的文字版，可以补一个结构化、不可变的 override 事件日志实体。
- **一次运行内所有子决策共享同一个基准快照点**（5.2.2）：在已有的"容量灯必须重新查询"规则之上，
  再加一条"同一波派发内的所有子判断必须引用同一次读数，不能波次内部混用不同时刻的读数"。

## 明确不建议迁移的部分

- 造价公式、定额换算、税率计算、费用构成层级本身——与软件项目无对应关系。
- "历史 run 永不覆盖"这类存储代价高的强纪律——软件的重算成本远低于造价重算，没必要照搬存储量级，
  但"可追溯快照"这个原则本身值得留。
- 高精度影子值/最大余数法分摊、参数分层注册表——价值真实但偏辅助性，不直接命中已知三个核心缺陷，
  优先级应排在后面，除非未来真的出现"按权重拆分容量配额"这类具体场景。

## 建议的落地顺序

1. **孤儿结论检测**（缺陷1对应模式）——影响最大，且已经有今天两个真实反例作为验收用例。
2. **DRAFT_ONLY 强制水印**——和第1条是一体两面，实现成本低（先定义必填字段清单）。
3. **不可变运行三元组快照**（缺陷2对应模式）——直接对症一个反复出现的已知缺陷。
4. 其余模式按团队实际遇到摩擦的频率决定是否投入。

本文档只是调研结论，不代表已授权实施——把任一条模式变成完善orca的实际治理机制，仍需按现有规则走
候选→复核→接受流程，不能因为"调研觉得有道理"就直接生效。
